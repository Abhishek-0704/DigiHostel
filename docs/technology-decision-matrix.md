# Technology Decision Matrix

Evaluated against `docs/architecture-requirements.md`, prioritized: (1) security, (2) SDD compliance, (3) maintainability, (4) reliability, (5) offline capability, (6) platform integration, (7) development velocity, (8) operational simplicity, (9) cost, (10) team skill requirements. Decisions materially affecting architecture are recorded as ADRs (`docs/adr/`); routine tooling choices are recorded here only.

| Decision | Candidates | Requirements | Selected | Why | Rejected Alternatives |
|---|---|---|---|---|---|
| Mobile framework | Flutter, React Native/Expo, native Android+iOS | Biometric, platform attestation, QR, background behavior, push, geolocation, offline storage, iOS/Android parity, two-app maintainability (ADR-001) | **React Native / Expo (TypeScript)** | Mature biometric (`expo-local-authentication`), attestation, camera/QR, push, and geolocation modules; managed workflow reduces two-app operational overhead; TypeScript unifies language across both mobile apps and the backend, enabling direct type/schema sharing (Zod) rather than dual-maintaining validation logic in two languages — a real, requirement-driven advantage given ADR-001 mandates two apps. See ADR-004. | **Flutter**: comparable capability, but Dart cannot share types/validators with a TS backend without codegen bridging, adding friction the two-app requirement makes worse, not better. **Native Android+iOS**: best possible platform integration but doubles engineering cost across two roles × two platforms (4 codebases) — not justified at MVP/pilot-hostel scale. |
| Backend language/framework | TypeScript+Node.js (Express/Fastify), Go | Security, realtime, concurrency, ecosystem, validation, testing, Supabase integration | **TypeScript + Node.js, Fastify** | TS backend + TS mobile = one language, direct Zod schema sharing via `lib/*` packages (matches `docs/api-contract.md`'s existing Zod/Orval contract strategy). Fastify's schema-first request/response validation hooks (`onRequest`/`preHandler`) map cleanly onto the required TLS→Auth→RBAC→business→DB→realtime→audit→response pipeline (SDD Ch.17.1) as named lifecycle hooks; native TS support avoids Express's bolt-on typing. Supabase's JS SDK is the most mature client available. See ADR-005. | **Go**: strong concurrency/security properties, but no type-sharing with the TS mobile clients (requires OpenAPI codegen either way, adding no advantage over TS), smaller Supabase-client maturity, and would fragment the team across two languages for no requirement-driven benefit. **Express**: viable, but Fastify's schema-hook model is a better structural fit for this project's validate-at-the-boundary and layered-pipeline requirements. |
| Database / backend platform | Supabase/PostgreSQL, managed PostgreSQL + custom services, other | RLS, realtime (named explicitly in SDD), auth primitives, storage, migrations, ops model, vendor coupling | **Supabase (PostgreSQL + Realtime + Storage)** | SDD names Supabase Realtime explicitly and repeatedly (Ch.3, Ch.7, Ch.8, Ch.11, Ch.13) — not a generic "some realtime service." RLS is a first-class requirement and Supabase/Postgres RLS is exactly the enforcement mechanism the SDD's security chapter assumes. Building custom realtime infrastructure (WebSocket fan-out, presence, change-data-capture) is substantial engineering effort not justified for an MVP/pilot-hostel team. Vendor coupling is a real, accepted tradeoff — see ADR-006. | **Managed Postgres + custom services**: more control, no vendor lock-in, but requires building and operating realtime infra from scratch and loses the integrated RLS+Realtime+Storage control plane the SDD's security model assumes. Not selected: the SDD's explicit, repeated naming of Supabase Realtime is treated as a real requirement, not incidental phrasing. |
| Auth strategy | Supabase Auth, fully custom, hybrid | Bespoke OTP+device-trust+biometric+attestation flow (Ch.4, Ch.17.2, ADR-003) | **Supabase Auth + PostgreSQL + Realtime + Storage, with Fastify as the business/API layer** (ADR-014, superseding this row's original conclusion) | Supabase Auth owns identity/session/JWT/refresh-token lifecycle — a solved problem it implements correctly, and the substrate RLS/Realtime already expect. The bespoke OTP-gated roll-number verification, device-trust, biometric, and platform-attestation flow is fully preserved, re-scoped as Fastify/Postgres business-authorization gates layered on top of a valid Supabase session, per `docs/auth-database-security-model.md`. | **Custom backend-issued JWT** (this row's original selection, ADR-006): reimplemented a solved problem, required hand-maintaining compatibility with RLS/Realtime's native JWT assumptions, and carried an avoidable long-lived signing secret — see ADR-014's Rationale for the full correction. |
| API style | REST, GraphQL, hybrid | Fixed, well-known mobile screens; OpenAPI-driven contract already mandated (`docs/api-contract.md`) | **REST + OpenAPI** | Matches `docs/api-contract.md` and `.claude/rules/api.md` exactly (`/api/v1`, JSON, versioned). No flexible/ad-hoc query requirement exists anywhere in the SDD to justify GraphQL's added complexity; REST's per-endpoint boundary maps cleanly onto RBAC and audit-logging requirements (one clear enforcement point per operation). See ADR-007. | **GraphQL**: added schema/resolver complexity and weaker fit with simple per-endpoint RBAC/audit enforcement; no SDD requirement justifies it. **Hybrid**: unnecessary complexity for this requirement set. |
| API validation / contract strategy | Shared TS schemas, OpenAPI+Orval+Zod, ad hoc validation | Contract-first validation, generated clients, `docs/api-contract.md`'s existing mandate | **OpenAPI (source contract) → Orval → generated Zod schemas + React Query client** | This is `docs/api-contract.md` and `.claude/rules/api.md`'s existing, governance-level mandate, arrived at here independently via the REST decision above — not a reuse of deleted code (no files are copied; the pattern is a documented convention, not an implementation artifact). Contract-first validation enforces "validate inputs at trust boundaries" (`.claude/rules/coding.md`) directly from the spec. See ADR-007. | **Ad hoc per-endpoint validation**: drifts from the spec over time, no generated-client guarantee of type safety. |
| Client state management | TanStack Query, Redux+RTK Query, SWR, plain fetch+hooks | Server-state caching, optimistic updates, realtime-driven cache invalidation | **TanStack Query (React Query)** | Pairs naturally with the Orval-generated hooks; strong optimistic-update and cache-invalidation primitives needed for approval/journey status updates driven by Supabase Realtime events. | **Redux+RTK Query**: more boilerplate for no additional capability this project needs. **SWR**: comparable but weaker generated-client tooling ecosystem than TanStack Query+Orval. |
| Offline persistence | expo-sqlite, MMKV+manual queue, WatermelonDB, RxDB | Encrypted local storage, offline event queue (Ch.9/10), no SDD-specified conflict strategy | **expo-sqlite (persisted queue) + TanStack Query persistence, server-authoritative conflict resolution** | Server is always the source of truth for state transitions (approvals, journey status); client offline actions queue locally and replay on reconnect, with optimistic UI that reverts on server rejection. This is a deliberate default addressing the SDD's confirmed gap (no conflict-resolution strategy specified anywhere). See ADR-008. | **WatermelonDB/RxDB**: powerful bidirectional sync engines, but heavier than this project's actual need (mobile clients mostly queue outbound actions and receive realtime pushes, not bidirectional multi-writer sync). |
| Realtime mechanism | Supabase Realtime (Postgres Changes + Broadcast), custom WebSocket, polling | Named explicitly by the SDD; approvals, journey status, notifications, dashboards, incident escalation | **Supabase Realtime** — Postgres Changes for state-table-driven updates (`leave_requests`, `journey_events`, `notifications`), Broadcast channels for transient events (incident escalation) | Matches the SDD's explicit, repeated naming; avoids building/operating custom realtime infrastructure. See ADR-009. | **Custom WebSocket service**: full control, but duplicates what Supabase already provides and adds real operational burden. **Polling**: explicitly rejected by the SDD itself ("Realtime... without client polling," Ch.11 §11.9). |
| Push notifications | Expo Push (FCM/APNs), direct FCM/APNs integration, third-party (OneSignal) | Both apps have a Notifications module; escalation timing-sensitive | **Expo Push Notifications** | Native fit given the Expo mobile decision; no added vendor beyond what's already chosen. | **Direct FCM/APNs**: more control, no material benefit given Expo already manages this well. **OneSignal**: unnecessary third-party dependency for a requirement Expo already covers. |
| Background jobs | pg-boss (Postgres-native), BullMQ+Redis, cloud cron | Escalation timers, notification retry; "operational simplicity" and "minimum dependency set" priorities | **pg-boss (runs on the existing Supabase Postgres)** | Avoids introducing Redis as a new infrastructure dependency purely for job queueing — reuses the database already required for everything else. Sufficient for escalation-timer and notification-retry volume at MVP/pilot scale. See ADR-011. | **BullMQ+Redis**: more throughput headroom, not needed at this scale, and adds an infrastructure component + secret to manage for no current benefit. **Cloud cron only**: insufficient for per-request escalation timers, which need per-row scheduling, not fixed-interval jobs. |
| Testing stack | Vitest, Jest, Playwright, Detox, Maestro | Unit/integration/API/DB/E2E/mobile per the testing pyramid (SDD Ch.15) | **Vitest** (unit/integration/API, TS-native, ESM-first) + **Playwright** (E2E for web dashboards) + **Maestro** (mobile E2E flows) | Vitest's TS-first design and speed fit a TS-only stack; Playwright is the standard for web E2E; Maestro's YAML-based flows have materially lower setup cost than Detox for a small team, at acceptable coverage for the mobile flows that matter (leave approval, QR journey). No dedicated ADR — routine tooling choice, does not constrain architecture. | **Jest**: viable but slower and more config overhead than Vitest for an ESM/TS-first codebase. **Detox**: more powerful but heavier setup/maintenance cost than justified here. |
| Monorepo/workspace strategy | pnpm workspaces, Nx, Turborepo, separate repos | `CLAUDE.md` mandates pnpm; multiple apps (ADR-001) + shared packages | **pnpm workspaces** (no Nx/Turborepo layer added yet) | `CLAUDE.md` Non-negotiables already mandates pnpm for this monorepo — not an independently re-derived choice, a governance constraint. Plain pnpm workspaces are sufficient at current scale (a handful of packages); an orchestration layer (Nx/Turborepo) can be added later if build-graph complexity grows, without being a structural blocker now. | **Nx/Turborepo**: real value at larger scale (caching, task graphs), but added complexity not justified for the current package count. **Separate repos**: breaks the shared-package/type-sharing strategy this decision matrix depends on throughout. |
| Package manager | pnpm | Mandated by `CLAUDE.md` | **pnpm** | Governance mandate, not evaluated as a free choice. | n/a |
| Deployment platform | Vercel+Supabase+GitHub, other cloud (AWS/GCP/self-hosted) | SDD explicitly specifies GitHub→Vercel→Supabase pipeline | **Vercel (backend/web) + Supabase (DB/Realtime/Storage) + GitHub (source/CI) + EAS (mobile builds/OTA)** | Matches the SDD's deployment chapter exactly (Ch.14); EAS is the natural addition given the Expo mobile decision (not SDD-specified, but a direct consequence of ADR-004). See ADR-013. | **AWS/GCP/self-hosted**: more control and no vendor coupling, but directly contradicts the SDD's explicit deployment specification with no requirement-driven justification to deviate. |
| CI/CD | GitHub Actions, other | GitHub already selected as source control | **GitHub Actions** | Native fit with GitHub; triggers typecheck/lint/test/build on PR, deploy on merge per `docs/deployment.md`'s branch model. Routine choice, covered under ADR-013 rather than its own ADR. | Other CI providers: no reason to introduce a second vendor when GitHub is already the source-control platform. |
| Observability | Structured logging (pino) + Supabase/Vercel dashboards; Sentry optional | MVP-stage logs/metrics (Ch.14); "operational simplicity" and "minimum dependency set" | **pino structured logging + Supabase/Vercel built-in dashboards now; Sentry recommended but deferred to implementation time**, not installed at scaffold time | Meets the MVP-stage requirement without adding tooling before it's needed; Sentry has high value-per-setup-cost for crash/error visibility and should be added early in implementation, but installing it during a "do not implement yet" phase would be premature. | Full APM (Datadog etc.): not justified at MVP scale. |
