# Realtime Security Model

Per ADR-009 (Realtime Architecture) and `docs/auth-database-security-model.md` §18. Covers every table/event that requires realtime delivery, per `docs/target-architecture.md`'s data flows.

| Table/Event | Actor(s) | Channel mechanism | Event(s) | Authorization rule | Sensitivity | Private channel required? |
|---|---|---|---|---|---|---|
| `leave_requests` status changes | student, linked parent(s)/guardian(s) | Postgres Changes | `UPDATE` on `status` | Inherits `docs/rls-policy-matrix.md`'s `leave_requests` SELECT policy automatically — a client only receives events for rows they could already `SELECT` | Medium (approval workflow state) | N/A — Postgres Changes is inherently RLS-scoped, not a discoverable-by-name channel |
| `leave_requests` status changes (staff view) | reception (own hostel), hostel_admin, super_admin | Postgres Changes | `UPDATE`/`INSERT` | Same RLS-inherited scoping, staff SELECT policy | Medium | N/A |

## General Rules

1. **Postgres Changes requires no separate authorization configuration** — it inherits whatever RLS already grants for `SELECT` on the underlying table. This is why the RLS matrix (`docs/rls-policy-matrix.md`) is the single source of truth for who receives which row-level realtime event; this document does not duplicate that logic, only names which tables actually need realtime delivery at all (most tables in the schema do not — e.g. `hostels`, `staff`, `trusted_devices` are not realtime-subscribed by any current requirement).
2. **Broadcast is reserved for transient, non-row events** (escalation timeouts, incident alerts) that don't map cleanly to "a row changed." Every Broadcast channel used by DigiHostel is a **private channel**, authorized via an RLS-style policy on `realtime.messages` scoped to the specific resource (a `leave_request_id` or `security_incidents.id`), never an open/public channel reachable by anyone who guesses or is told the channel name.
3. **No approval or escalation event is ever exposed through a publicly discoverable channel**, per this task's explicit instruction — every channel above with sensitivity Medium or higher is either RLS-inherited (Postgres Changes) or an explicitly private, policy-gated Broadcast channel.
4. Realtime authorization always uses the client's own Supabase session (ADR-014) — never a shared or service-role credential on a mobile client, consistent with `docs/target-architecture.md`'s trust boundaries.

## Flagged for Spot-Check

Per ADR-014's methodology caveat (web research tools unavailable for this and the prior task): the exact current mechanism/API surface for RLS-gated Realtime Broadcast (`realtime.messages` policy shape, private-channel declaration on the client SDK) should be confirmed against current `supabase.com/docs/guides/realtime/authorization` before implementation — this document asserts the *existence, purpose, and required scope* of that control with confidence, not its exact current configuration syntax.
