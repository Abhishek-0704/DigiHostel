## Current implementation state

Following the reset, the workspace was scaffolded (ADR-001 through ADR-013), then a real authentication/authorization boundary was implemented (ADR-014), then the workspace package build/runtime-resolution issue was fixed, then the first real business workflow — Parent Leave Approval — was implemented end-to-end, then extended with the student-facing side (Student Leave Request creation/viewing), then hardened and verified (Parent/Guardian Leave Approval Hardening — expanded authorization test coverage, no new mechanisms), then the leave-escalation/notification domain was designed (ADR-016 proposed), then a correction pass re-verified that design and split the orchestration ADR in two (ADR-017 leave-side, ADR-018 notification-side, new, per SDD Ch.11 §11.3's own service split), then a governance-resolution pass **finalized and accepted all three ADRs** (ADR-016, ADR-017, ADR-018), then a final consistency-correction pass found ADR-017 §9 factually wrong (it omitted the `in_app_call` stage and invented an unevidenced `expired`-trigger claim) and corrected it via a new, narrowly-scoped superseding ADR (**ADR-019**, ACCEPTED, superseding only ADR-017 §9's transition-sequencing claims — see `docs/leave-escalation-notification-design.md`), then the repository's own post-reset baseline (previously only ever a working-tree diff) was committed for the first time, then — once the product supplied the two previously-blocking values (90s uniform per-stage escalation interval; notification retry policy of 1 initial attempt + 3 retries at 30s/60s/120s, exponential, capped at 120s, max 4 provider attempts) — the **leave-escalation scheduler and notification delivery worker were implemented end-to-end** against ADR-017/ADR-018/ADR-019's mechanics, then two independent audits (Prompt 0.5, Prompt 0.6) established an evidence-based backend-readiness baseline and gap register, then a **critical-remediation pass (Prompt 0.7)** closed the highest-priority findings: a global Fastify error handler (G-01) now sanitizes every unexpected exception; tiered rate limiting (G-02) now protects every sensitive route; the OTP delivery mechanism was decided (**ADR-020**, ACCEPTED — Supabase Auth's native phone-OTP flow, SMS-provider selection explicitly left open); a parent-scoped `GET /leave-requests` (G-05) now lets an authenticated parent/guardian retrieve every linked student's leave requests; and device attestation (G-04) was assessed and explicitly documented as **not implemented**, not silently left ambiguous. See `docs/target-architecture.md`, `docs/workspace-structure.md`, `docs/auth-database-security-model.md`, and `docs/leave-approval-workflow.md` for the reasoning behind the earlier decisions. The Parent + Guardian mobile application was then built out end-to-end (Authentication/OTP, Trusted Devices, Biometric, Security Center, Dashboard, Notifications, backend-integrated Leave Approval and Approval History, then Profile/Settings/Account Management — `apps/parent-mobile/docs/foundation.md` §7–§17), followed by a **release-hardening pass (Phase 5 Prompt 12, RC1)** that fixed a data-correctness blocker (an unfiltered "pending leave" count), a backend security gap (biometric step-up assertions were not bound to the specific leave request they were captured for), realtime-reconnect/query-resume reliability gaps, CORS/test-route production hardening, and a handful of code-quality/accessibility issues — see `apps/parent-mobile/docs/rc1-hardening.md` for the full inventory. That pass also **discovered a new, unresolved production blocker**: the real Login/OTP screen (commit `c8a8fc1`) now calls Supabase's `signInWithOtp` directly for any syntactically-valid phone number, with no server-side pre-check that the number belongs to a registered parent and no effective (non-client-side) rate limiting — exactly the gap ADR-020 had already named and deferred, now live rather than merely anticipated.

- **Trusted-device RLS bypass — discovered by the Phase 13 Production Readiness Review (Finding F-01), remediated the same phase.** The `trusted_devices` table previously carried an `authenticated`-role INSERT policy (`trusted_devices_insert_own`) that let any authenticated parent self-insert a fully **active** device row with no attestation check at all — the exact bypass ADR-003's mandatory gate exists to prevent, and a live database-level authorization gap independent of anything the mobile app's own client code chose to implement. **Remediated**: that INSERT policy has been removed entirely (`supabase/migrations/0003_f01_trusted_devices_rls_remediation.sql`) — `authenticated` now has no INSERT path onto this table at all, matching `device_attestation_events`'s existing insert-only-via-backend pattern. The remaining self-revoke UPDATE policy was also tightened to a one-way active→revoked transition on `revoked_at`/`revoked_reason` only, with a `BEFORE UPDATE` trigger (`trusted_devices_revoke_only`) blocking any other column from being smuggled into the same statement. See `docs/f01-trusted-device-remediation.md` for the full remediation report, including the still-open limitation this fix does **not** address: real, cryptographic device attestation (ADR-003) remains unimplemented — this remediation only closes the RLS-level self-authorization bypass, it does not make attestation exist.

## Important distinction

The SDD describes the target design. This file describes verified repository reality.

Do not assume an SDD endpoint, workflow, table, dashboard, or integration exists merely because it is specified in the SDD.

Do not assume anything from the deleted Replit implementation (former `artifacts/`, `lib/`, `scripts/` directories, package versions, dependency choices, database schema, or API routes) reflects the current or future implementation. It is not an authoritative baseline — see `docs/implementation-baseline.md` and `docs/adr/`. The current `apps/`/`packages/` scaffold was independently designed per the ADRs in `docs/adr/`, not copied from the deleted implementation, even where naming or shape is similar for genuinely justified reasons (see `docs/workspace-structure.md`'s naming rationale).
