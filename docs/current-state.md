# Current Repository State

This document records verified implementation facts and should be updated when the repository changes materially.

> This document describes the current post-reset repository state. The previous Replit implementation was intentionally discarded and is not part of the current implementation baseline.

## Current implementation state

Following the reset, the workspace was scaffolded (ADR-001 through ADR-013), then a real authentication/authorization boundary was implemented (ADR-014), then the workspace package build/runtime-resolution issue was fixed, then the first real business workflow — Parent Leave Approval — was implemented end-to-end, then extended with the student-facing side (Student Leave Request creation/viewing), then hardened and verified (Parent/Guardian Leave Approval Hardening — expanded authorization test coverage, no new mechanisms), then the leave-escalation/notification domain was designed (ADR-016 proposed), then a correction pass re-verified that design and split the orchestration ADR in two (ADR-017 leave-side, ADR-018 notification-side, new, per SDD Ch.11 §11.3's own service split), then a governance-resolution pass **finalized and accepted all three ADRs** (ADR-016, ADR-017, ADR-018), then a final consistency-correction pass found ADR-017 §9 factually wrong (it omitted the `in_app_call` stage and invented an unevidenced `expired`-trigger claim) and corrected it via a new, narrowly-scoped superseding ADR (**ADR-019**, ACCEPTED, superseding only ADR-017 §9's transition-sequencing claims — see `docs/leave-escalation-notification-design.md`), leaving only two external product-parameter decisions (escalation-interval duration, notification retry policy) and one specified-but-not-yet-created migration before implementation can begin. **No implementation code, schema, or dependency has changed across any of these design/governance tasks.** See `docs/target-architecture.md`, `docs/workspace-structure.md`, `docs/auth-database-security-model.md`, and `docs/leave-approval-workflow.md` for the reasoning behind each.

Verified baseline:
- pnpm monorepo (`apps/*`, `packages/*`) — pnpm resolved via corepack to 11.25.0 in this environment; no `packageManager` field pinned yet.
- Node 24.19.0 (this environment) — no project-level version pin recorded yet.
- `apps/api`: Fastify backend (ADR-005). Routes: `GET /api/v1/healthz`; `POST/GET /api/v1/leave-requests` (student create/list own); `GET/approve/reject /api/v1/leave-requests/{leaveRequestId}` (owning student or authorized parent/guardian for GET, parent/guardian-only for approve/reject — `docs/leave-approval-workflow.md`); `/api/v1/_internal/*` (auth-boundary demonstration routes, not part of the product API contract).
- **Authentication**: real, per ADR-014 — Supabase JWT verification via `jose`/JWKS (`apps/api/src/lib/auth/jwt.ts`), empirically confirmed against the local Supabase instance's live JWKS endpoint. **Authorization**: role guards + PostgreSQL-resolved relationship/scope checks (`apps/api/src/lib/auth/guards.ts`) — never a JWT claim beyond coarse role/own-id.
- **Database schema**: real, per ADR-002/ADR-015 — 17 tables (`packages/db/src/schema/`), RLS enabled and policy-covered on every table, verified by 41 passing pgTAP assertions (`supabase/tests/database/`, `docs/rls-policy-matrix.md`), unchanged by the student leave-request work (no migration was needed — the student `INSERT`/`SELECT own` RLS policies on `leave_requests` already existed). `packages/db` now builds real `dist/` output consumable by plain Node at runtime (previously it did not — fixed).
- `packages/api-spec`, `packages/api-zod`, `packages/api-client-react`: OpenAPI-first contract pipeline (ADR-007), covering health-check + the five leave-workflow endpoints (student create/list, get-by-id, approve, reject); Orval codegen verified to run and produce correct output after each contract change.
- `apps/student-mobile`, `apps/parent-mobile`: Expo/React Native scaffolds (ADR-004), default template screen only, no product screens — unchanged by any of the above.
- `pnpm install`, `pnpm run typecheck` (all 7 packages), `pnpm run lint`, `pnpm run format`, `pnpm test` (98 passing, 11 skipped — the Postgres-dependent leave integration suite, which was separately run and verified against local Supabase), `pnpm run build` (including an automated workspace-package runtime-resolution check) all verified passing in this environment. The compiled `node apps/api/dist/index.js` was started directly (no TypeScript loader) and smoke-tested against `/healthz`, a real authenticated student leave-request creation, list, and get-by-id, and (in the prior task) a real authenticated leave-approval decision — all using real local Supabase Auth sessions.

There is still:
- No mobile UI, push notifications, escalation scheduler, real biometric provider, SIM verification, device attestation provider, realtime events, or library workflow — all explicitly out of scope for the work done so far; see `docs/leave-approval-workflow.md` and `docs/auth-database-security-model.md` for the interfaces already in place for future integration.
- No deployment infrastructure beyond the scaffolded config referenced in ADR-013.
- The leave-approval workflow's biometric confirmation step is an explicitly non-cryptographic placeholder (`AssertionPresenceBiometricFreshnessGate`) — flagged as a genuine, unresolved item, not equivalent to real verification.
- No duplicate/overlapping-leave-request restriction, and no modification/cancellation path — neither the SDD nor the current schema defines either, so neither was invented (`docs/leave-approval-workflow.md`'s "Student Leave Request Creation" section).
- Any linked parent/guardian (regardless of `relationship_type`/`escalation_order`) may decide a leave request, not only "the current escalation step's party" — this is now the **formally accepted** design ([ADR-016](adr/ADR-016-leave-escalation-approval-authority.md), Model C). No code change was needed — this ratifies already-implemented, already-tested behavior.
- The leave-escalation scheduler, notification delivery (Expo Push), pg-boss workers, and realtime escalation events remain **designed and formally accepted at the ADR level, but not yet implemented** — `docs/leave-escalation-notification-design.md`'s final 26-row decision matrix, and ADR-016/ADR-017/ADR-018/ADR-019, are all now `ACCEPTED`. The automated escalation chain, corrected by ADR-019, advances `guardian_notified` → `in_app_call` → `manual_verification`; `expired` is reached only by explicit staff action from `manual_verification`, never an automatic timer. **Two genuinely external decisions block actual implementation**, neither resolvable by an ADR: the exact escalation-interval duration and the exact notification retry-count/backoff schedule (both `PROPOSED — PRODUCT DECISION REQUIRED`; no assumption of a specific value, e.g. "1.5 minutes," is sourced from this repository, confirmed by full-text search across four separate tasks). **One small, fully specified migration is also a concrete prerequisite** for the notification side specifically (a `notifications.stage` column + uniqueness constraint, ADR-017 §5) — decided, not yet created (out of scope for any design-only task). No implementation code has changed.

## Important distinction

The SDD describes the target design. This file describes verified repository reality.

Do not assume an SDD endpoint, workflow, table, dashboard, or integration exists merely because it is specified in the SDD.

Do not assume anything from the deleted Replit implementation (former `artifacts/`, `lib/`, `scripts/` directories, package versions, dependency choices, database schema, or API routes) reflects the current or future implementation. It is not an authoritative baseline — see `docs/implementation-baseline.md` and `docs/adr/`. The current `apps/`/`packages/` scaffold was independently designed per the ADRs in `docs/adr/`, not copied from the deleted implementation, even where naming or shape is similar for genuinely justified reasons (see `docs/workspace-structure.md`'s naming rationale).
