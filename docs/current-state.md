- **Unauthenticated SMS-OTP triggering — discovered by the Phase 13 Production Readiness Review (Finding F-02), remediated the same phase.** `apps/parent-mobile/app/(auth)/login.tsx` previously called `signInWithOtp` directly for any syntactically-valid phone number, with no server-side pre-check and only a 30-second client-side cooldown (not a security control) — the exact gap ADR-020 had named and deferred. **Remediated**: the client no longer collects or submits a phone number at all; it submits a roll number + relationship to a new backend eligibility gate (`POST /api/v1/auth/otp/request`, `apps/api/src/domain/auth/`), which resolves the authoritative phone server-side (`students` → `parent_student_relationships` → `parents`) and only then dispatches an OTP via its own anon-keyed Supabase client — `shouldCreateUser: false` as a secondary defense, IP-keyed rate-limit tiers on both new endpoints (`RATE_LIMIT_OTP_REQUEST`/`RATE_LIMIT_OTP_VERIFY`, `apps/api/src/config/rateLimit.ts`), and a constant response shape regardless of eligibility (anti-enumeration). Verification then confirmed the fix at every applicable evidence tier — CODE, UNIT/INTEGRATION (backend service + route tests), real-Postgres INTEGRATION (`eligibilityRepository.integration.test.ts`, including the ADR-016 duplicate-relationship tie-break), and a LOCAL SUPABASE live smoke test against the actual running Auth instance (never real production SMS). No service-role key was introduced anywhere. See `apps/parent-mobile/docs/authentication.md` §2 for the full new flow and `apps/parent-mobile/docs/rc1-hardening.md` §4 for the original finding.
