# Current Repository State

This document records verified implementation facts and should be updated when the repository changes materially.

> This document describes the current post-reset repository state. The previous Replit implementation was intentionally discarded and is not part of the current implementation baseline.

## Current implementation state

Following the reset, the workspace was scaffolded (ADR-001 through ADR-013), then a real authentication/authorization boundary was implemented (ADR-014), then the workspace package build/runtime-resolution issue was fixed, then the first real business workflow — Parent Leave Approval — was implemented end-to-end, then extended with the student-facing side (Student Leave Request creation/viewing), then hardened and verified (Parent/Guardian Leave Approval Hardening — expanded authorization test coverage, no new mechanisms), then the leave-escalation/notification domain was designed (ADR-016 proposed), then a correction pass re-verified that design and split the orchestration ADR in two (ADR-017 leave-side, ADR-018 notification-side, new, per SDD Ch.11 §11.3's own service split), then a governance-resolution pass **finalized and accepted all three ADRs** (ADR-016, ADR-017, ADR-018), then a final consistency-correction pass found ADR-017 §9 factually wrong (it omitted the `in_app_call` stage and invented an unevidenced `expired`-trigger claim) and corrected it via a new, narrowly-scoped superseding ADR (**ADR-019**, ACCEPTED, superseding only ADR-017 §9's transition-sequencing claims — see `docs/leave-escalation-notification-design.md`), then the repository's own post-reset baseline (previously only ever a working-tree diff) was committed for the first time, then — once the product supplied the two previously-blocking values (90s uniform per-stage escalation interval; notification retry policy of 1 initial attempt + 3 retries at 30s/60s/120s, exponential, capped at 120s, max 4 provider attempts) — the **leave-escalation scheduler and notification delivery worker were implemented end-to-end** against ADR-017/ADR-018/ADR-019's mechanics, then two independent audits (Prompt 0.5, Prompt 0.6) established an evidence-based backend-readiness baseline and gap register, then a **critical-remediation pass (Prompt 0.7)** closed the highest-priority findings: a global Fastify error handler (G-01) now sanitizes every unexpected exception; tiered rate limiting (G-02) now protects every sensitive route; the OTP delivery mechanism was decided (**ADR-020**, ACCEPTED — Supabase Auth's native phone-OTP flow, SMS-provider selection explicitly left open); a parent-scoped `GET /leave-requests` (G-05) now lets an authenticated parent/guardian retrieve every linked student's leave requests; and device attestation (G-04) was assessed and explicitly documented as **not implemented**, not silently left ambiguous. See `docs/target-architecture.md`, `docs/workspace-structure.md`, `docs/auth-database-security-model.md`, and `docs/leave-approval-workflow.md` for the reasoning behind the earlier decisions.

Verified baseline:
- pnpm monorepo (`apps/*`, `packages/*`) — pnpm resolved via corepack to 11.25.0 in this environment; no `packageManager` field pinned yet.
- Node 24.19.0 (this environment) — no project-level version pin recorded yet.
- `apps/api`: Fastify backend (ADR-005). Routes: `GET /api/v1/healthz` (rate-limit exempt); `POST /api/v1/leave-requests` (student create); `GET /api/v1/leave-requests` (student's own, **or** — since Prompt 0.7 (G-05) — an authenticated parent/guardian's every linked student's requests, scoped entirely by the caller's own resolved identity, never a client-supplied filter; an unrelated/unlinked parent gets an empty array, not an error); `GET/approve/reject /api/v1/leave-requests/{leaveRequestId}` (owning student or authorized parent/guardian for GET, parent/guardian-only for approve/reject — `docs/leave-approval-workflow.md`); `POST /api/v1/leave-requests/{leaveRequestId}/expire` (staff-only, hostel-scoped); `/api/v1/_internal/*` (auth-boundary demonstration routes, not part of the product API contract). Every mutating/sensitive route also carries a per-sensitivity-tier rate limit (`apps/api/src/config/rateLimit.ts`, `apps/api/src/plugins/rateLimit.ts` — G-02); a global Fastify error handler (`apps/api/src/lib/errorHandler.ts` — G-01) ensures any exception not already mapped to a typed response collapses to a fixed, generic 500 with no internal detail, verified against the installed Fastify version's actual default-handler behavior (which does **not** sanitize unhandled errors on its own) rather than assumed.
- **Authentication**: real, per ADR-014 — Supabase JWT verification via `jose`/JWKS (`apps/api/src/lib/auth/jwt.ts`), empirically confirmed against the local Supabase instance's live JWKS endpoint. **Authorization**: role guards + PostgreSQL-resolved relationship/scope checks (`apps/api/src/lib/auth/guards.ts`) — never a JWT claim beyond coarse role/own-id. **OTP mechanism**: decided (**ADR-020**, ACCEPTED) — Supabase Auth's native phone-OTP flow; not yet implemented (no mobile app exists to implement a Login/OTP screen against it yet). **Device attestation** (ADR-003): assessed, not implemented — see the "There is still" list below for the precise, explicit status.
- **Database schema**: real, per ADR-002/ADR-015 — 17 tables (`packages/db/src/schema/`), RLS enabled and policy-covered on every table, verified by 45 passing pgTAP assertions (`supabase/tests/database/`, `docs/rls-policy-matrix.md`). `packages/db` builds real `dist/` output consumable by plain Node at runtime. Two columns added by migration `0001` for the escalation/notification work: `trusted_devices.expo_push_token` (nullable — populated by a future parent-mobile device-registration flow, out of scope here) and `notifications.stage` (nullable, mirrors `leave_request_status`) plus a uniqueness constraint on `(related_leave_request_id, recipient_id, stage)` (ADR-017 §5/ADR-018 §1's notification-identity prerequisite).
- **Leave escalation scheduler + notification delivery** (ADR-017/ADR-018/ADR-019) — real, pg-boss-backed (`apps/api/src/workers/{escalationWorker,notificationWorker}.ts`, `apps/api/src/domain/{leave,notification}/*`, `apps/api/src/lib/{queue,push}/*`). `LeaveRepository.create()` now schedules the first `leave-escalation-stage-evaluate` job in the same transaction as the insert (via pg-boss's Drizzle transaction adapter); `advanceEscalation()` implements the corrected `pending → father_notified → mother_notified → guardian_notified → in_app_call → manual_verification` chain (ADR-019 §1) with conditional-UPDATE race resolution (ADR-017 §4) and same-transaction follow-up job scheduling (ADR-017 §7); a new staff-only `POST /leave-requests/{id}/expire` (`markExpired()`) implements ADR-019 §2's exclusively-staff-triggered terminal transition, hostel-scoped for `reception_warden`/`hostel_admin`, unscoped for `super_admin` (enforced in application code, since Fastify's connection bypasses RLS). The notification worker resolves recipients by relationship type per stage (father/mother/guardian; `in_app_call` fans out to every linked parent/guardian — an implementation-level judgment call, not an ADR requirement, since no SDD/ADR text defines `in_app_call`'s actual recipients), and implements ADR-018 §2–§5's retry-count-gated conditional claim, 1-initial-attempt-plus-3-retries policy (30s/60s/120s, exponential, capped at 120s — product-supplied values), and three-provider-outcome handling via `expo-server-sdk`. Config (`apps/api/src/config/escalation.ts`) is named/env-overridable, not hard-coded, per ADR-017 §2. End-to-end verified against a real local Supabase + pg-boss instance (see Verification below) — not merely unit-tested.
- `packages/api-spec`, `packages/api-zod`, `packages/api-client-react`: OpenAPI-first contract pipeline (ADR-007), covering health-check + the six leave-workflow endpoints (student create/list, get-by-id, approve, reject, and the staff-only expire — `listLeaveRequests`'s spec description updated for the Prompt 0.7 parent-scoping change, G-05); Orval codegen re-run and verified to produce correct output after every contract change, including this task's.
- `apps/student-mobile`, `apps/parent-mobile`: Expo/React Native scaffolds (ADR-004), default template screen only, no product screens — unchanged by any of the above.
- `pnpm install`, `pnpm run typecheck` (all 7 packages), `pnpm run lint`, `pnpm run format`, `pnpm test` (160 passing — 0 skipped when `DATABASE_URL` is set, including the Postgres-dependent leave integration suite, and including the new error-handler and rate-limit test files added in Prompt 0.7), `pnpm run build` (including the automated workspace-package runtime-resolution check), and `supabase test db` (45/45 pgTAP, unaffected by Prompt 0.7 — no schema/RLS change was made) all verified passing in this environment. The compiled `node apps/api/dist/index.js` was started directly (no TypeScript loader) and smoke-tested end-to-end against a real local Supabase Auth session: a real leave request was created, a real escalation timer (temporarily lowered to 3s for the smoke run) advanced it automatically through every stage exactly as ADR-019 specifies (`father_notified → mother_notified → guardian_notified → in_app_call → manual_verification`, stopping there with no automatic `expired` transition), real `notifications` rows were created with correct per-stage recipients, and a real staff session then transitioned `manual_verification → expired` via `/expire` — all against the actual running pg-boss/Postgres stack, not a fake.

There is still:
- No real Expo push tokens exist anywhere in this environment (`trusted_devices.expo_push_token` is populated by a parent-mobile device-registration flow that doesn't exist yet — a separate workstream) — the notification worker correctly treats "no token" as an ordinary delivery rejection and retries/exhausts per policy, but no push has ever actually reached a device in this repository's history.
- `manual_verification`'s staff-facing notification (e.g. alerting reception when a request reaches the Manual Verification Queue) is explicitly not implemented — no ADR or SDD text defines its content/recipient, and no reception dashboard exists to receive it yet.
- **Device attestation (ADR-003, mandatory) — explicitly assessed (Prompt 0.7, G-04) and confirmed NOT implemented, not a placeholder claiming otherwise.** `apps/api/src/lib/auth/security-gates.ts`'s `DeviceAttestationGate` interface and `NotImplementedAttestationGate` (which throws `DeviceAttestationNotImplementedError` rather than silently passing — verified unchanged) are the only backend-side artifacts; nothing writes to `device_attestation_events`, and no Fastify route exists for a client to submit a Play Integrity/App Attest/DeviceCheck result to in the first place, because no device-registration endpoint exists yet (a separate, not-yet-built workstream — the trusted-device tables/RLS are designed for a client to write `trusted_devices` directly, per that table's own schema comment). Production implication: the trusted-device *registration* flow cannot be built to ADR-003's spec until (a) a device-registration integration point exists and (b) it calls into a real attestation verification (Google Play Integrity API / Apple App Attest API) — both are Parent-mobile-application-phase + backend-workstream dependencies, not decided or built here.
- No mobile UI, real biometric provider, SIM verification, realtime events, or library workflow — all explicitly out of scope for the work done so far; see `docs/leave-approval-workflow.md` and `docs/auth-database-security-model.md` for the interfaces already in place for future integration.
- No deployment infrastructure beyond the scaffolded config referenced in ADR-013. No CI/CD pipeline exists.
- The leave-approval workflow's biometric confirmation step is an explicitly non-cryptographic placeholder (`AssertionPresenceBiometricFreshnessGate`) — flagged as a genuine, unresolved item, not equivalent to real verification. Acceptable for development and a closed staging pilot; not acceptable for production (Prompt 0.6 audit, G-03) — not remediated by Prompt 0.7 (explicitly out of that task's scope).
- The notification worker's claim→provider-send→reschedule sequence is not transactionally atomic; a crash in that narrow window can leave a notification stuck, unretried, with no reaper to recover it (Prompt 0.6 audit, G-07) — not remediated by Prompt 0.7 (explicitly out of that task's scope).
- No duplicate/overlapping-leave-request restriction, and no modification/cancellation path — neither the SDD nor the current schema defines either, so neither was invented (`docs/leave-approval-workflow.md`'s "Student Leave Request Creation" section).
- Any linked parent/guardian (regardless of `relationship_type`/`escalation_order`) may decide a leave request, not only "the current escalation step's party" — the **formally accepted** design ([ADR-016](adr/ADR-016-leave-escalation-approval-authority.md), Model C), unaffected by the scheduler work above.
- The job-enqueue transaction boundary uses pg-boss's Drizzle adapter to genuinely share the same transaction as the state mutation (ADR-017 §7) — a stronger guarantee than the "commit, then enqueue" fallback originally anticipated, since the adapter turned out to exist in the installed pg-boss version.
- Production SMS-provider selection for OTP delivery (ADR-020) remains an explicitly open, tracked pre-production decision — not a pre-development blocker.

## Important distinction

The SDD describes the target design. This file describes verified repository reality.

Do not assume an SDD endpoint, workflow, table, dashboard, or integration exists merely because it is specified in the SDD.

Do not assume anything from the deleted Replit implementation (former `artifacts/`, `lib/`, `scripts/` directories, package versions, dependency choices, database schema, or API routes) reflects the current or future implementation.
